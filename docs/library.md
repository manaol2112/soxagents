# The standard library

The standard library is the firm's reusable methodology: for each standard control, what it is meant to achieve, how it is designed, the procedures that test it in each phase, the attributes those procedures test, the evidence they need, and the sources each rests on. An engagement plans from it; a person approves every plan ([testing.md](testing.md#master-test-plans-0079)).

## Where the library lives

The library's content is code, and stays so (decided by the product owner, milestone L1):

- `controls.py`: each standard control's record (ID, area, title, risk, activity, frequency, nature, evidence items), library version 4; the controls added in version 4 (`V4_LIBRARY`) carry no attributes of their own and take them from their definitions;
- `definitions_itgc_access.py`, `definitions_itgc_change.py`, `definitions_itgc_operations.py`, `definitions_itgc_more.py` (the IT general controls, version 4), `definitions_itac.py` and `definitions_ipe.py` (the application controls and key reports added in version 4), `definitions_itgc.py` (the entity-level, application, and key report controls of version 3, and the composed list) and `definitions_business.py`, read through `definition_registry.py`: each control's testing definition: objective, control type, performer and reviewer, trigger, population and sampling, procedures per phase (design, operating, roll-forward) with the attributes each tests, and each attribute's condition, rationale, evidence, data to extract, decision rules (passes, exception, insufficient, a person decides, never inferred), sources, and confidence. A version 4 definition also carries its procedures as numbered steps and its standard evidence suite (below);
- `statements_itgc.py`, `statements_itgc_more.py` (the controls added in version 4), and `statements_business.py`, read through `statement_registry.py`: each control's design statement, with the client's values as named slots;
- `testing_definitions.SOURCES`: what each cited source says, as read.

Code is version-controlled, checked by `definition_registry.problems` and `test_testing_definitions.py` (every attribute tested by a procedure, no vague wording, no unknown source), and published as [testing-definitions.md](testing-definitions.md), which a test keeps equal to the code. A database editor would duplicate those checks and lose the history; the governance below records decisions about the code, not copies of it.

An attribute's **confidence** is the library's own provenance: HIGH and MODERATE attributes are tested as the library's approved attributes; LOW and NOT_ESTABLISHED attributes are decided with the standard in the firm's library review, not plan by plan: they enter an engagement approved, each with its question as a note, and testing waits for any client value they show in brackets (milestone L3e, migration 0085; before L3e they entered as proposals, [testing-framework-review.md](testing-framework-review.md)).

## Governance (migration 0083)

A firm records, per standard control, where its methodology review stands: `library_entries` holds one row per organization and library key with a status, the library version it was decided on, a note, who decided and when, and the last approval (who, when, at which version). The statuses are:

| Status | Meaning |
| --- | --- |
| Draft | Not ready for review. |
| Pending methodology review | The published definition is a reviewer's draft. **A control with no row reads as pending review.** |
| Approved | A reviewer approved this library version as the firm's methodology. |
| Superseded | Approved at an earlier library version; the current version awaits approval. Derived from the approval's version, never stored. |
| Retired | Not to be used for new plans. |

Every member of the firm reads the library (`organization.read`). An owner or admin decides a status (`organization.update`), as for the firm's other settings; the decision is refused when it repeats the current status, so nothing is overwritten without a change, and each one writes a `library.status` audit event with the status before and after. Approving records the approver and the version; the last approval stays on the row when the entry later moves on. On the Library page an owner or admin can also select standard controls awaiting approval (pending review, or superseded) by row, by area, or all shown, and approve them together with one optional note (`PUT /library/status`, milestone L3e): all or none, each recorded and audited on its own as above, one already approved skipped.

**Change requests.** Any member may propose a change to a standard control, its retirement, or a new standard control (`library_change_requests`: kind, title, detail of at least twenty characters). An owner or admin accepts or declines it with a note; `library.change_request` and `library.change_decision` audit events record both. Deciding never edits the library: an accepted change is applied in code, reviewed like the rest, and arrives with the next library version, when the entry reads as superseded until approved again.

**What governance does not do yet.** The status is recorded and shown; nothing in an engagement reads it. Engagements still load, plan from, and test every library control as before. Limiting matches and new plans to approved templates is the matching milestone's (L2), so that it lands together with the match a person confirms.

## The Library page

The **Library** section of the workspace, under Setup, needs no engagement.

- The index: how many standard controls stand in each status (each figure filters the list), the five categories (IT general controls, application controls, key reports and IPE, business process controls, entity-level controls), a search over ID, title, area, and objective, and the controls by area, one line each: ID, title, nature, frequency, type, how many procedures and attributes, how many engagements have it in scope, and its status. Proposed new standard controls are listed beneath.
- One control: the control, its status and the last decision, the objective and risk, then six views: **Procedures** by phase, each with its action, evidence, and the attributes it tests; **Attributes**, the tested ones and then those proposed to each engagement with their question, each with its condition, decision rules, evidence, and source; **Evidence**, what an engagement requests and what each procedure needs; **Design**, the statement with the client's values in brackets, who performs and reviews it, its precision and investigation, the information it uses, the IT general controls it relies on, and the client values with which ones hold testing; **Sources**, what each says, as read; **Usage**, the firm's engagements that have it in scope. Applicability (when the control does not apply, the design to confirm, open questions, assumptions, retired attributes) folds beneath; the change requests, with the form to propose one and the buttons to decide one, close the page.
- An owner or admin sees the decision for where the entry stands: approve; send back to draft, withdraw approval, or retire, each with the reason on the record; submit a draft for review; approve a superseded entry's current version; reinstate a retired one for review.

API: `GET /organizations/{organization_id}/library`, `GET …/library/{library_key}`, `PUT …/library/{library_key}/status`, `GET` and `POST …/library/change-requests`, `PUT …/library/change-requests/{id}`. Web: `library-model.ts` (parsing, filters, the decisions offered, addresses, the calls), `load-library.ts`, `library-view.tsx`, the route `/workspace/library`.

## Test basis and matching (milestone L2, migration 0084)

A person decides, per control, what its test plan is built from (`engagement_controls.test_basis`, with who decided, when, and why):

| Basis | Meaning | What the plan does |
| --- | --- | --- |
| **Standard** | The matched standard governs. | Its procedures and attributes, with the client's values filled where the control states them. A procedure a person wrote or reworded is a finding on the plan review (`DEVIATES_FROM_STANDARD`). |
| **Customized standard** | The standard is the starting point; the firm tailors it. | The same proposals; edits are recorded as the person's, with no deviation finding. |
| **Client's procedures** | The client's documented procedures govern. | The standard is reference only: the planner does not apply the library definition and builds the plan from the control's own facts and attributes. |

With no decision, a library copy follows its standard and a client's control follows the client's procedures (`controls.basis_of`). Nothing is forced. Decided by the product owner.

**Matching** (`library_matching.py`) runs only when a person asks on the control (decided by the product owner: no import hook, no background worker). The fixed rules shortlist the standards of the control's category and area and score each on the words the control's title, activity, and risk share with the standard's title, objective, activity, statement, and attributes; on the nature fitting (a configuration is not a person's act); on the frequency; and on the signals that name a standard (a leaver, a transport, a three-way match), the specific standard displacing the general one. The top candidate is **Strong** when the score is high with a clear margin or a signal fired and the nature fits, **Partial** when the score is fair, **None** otherwise; retired standards are never offered, and no number is presented as a calibrated confidence. When a model is configured it adjudicates the shortlist (`ADJUDICATE_SCHEMA`): the match or none, its status, the rationale in the control's own words, the attributes that apply and those excluded with why, and what the control does not state. The answer is checked before it is used (`check_adjudication`): only a shortlisted standard, only real attribute keys, no attribute both applicable and excluded, and no threshold or deadline in the rationale that the control does not give; otherwise the rules' candidates stand, with the note. The run and its candidates are kept (`library_match_runs`, `library_matches`) and the run is an audit event (`library.match`).

The rules are calibrated by `test_library_matching.py`: thirteen controls written in a client RCM's wording (SAP provisioning, Workday termination, a quarterly access review, firefighter access, an emergency change, SAP transports, batch jobs, an Oracle three-way match, account reconciliations, a revenue flux review, an aged receivables report, a journal listing, a bank reconciliation) each find their standard as a strong candidate, and two the library does not have (stock-based compensation, a pricing configuration) are not called strong.

**Following a standard** the control does not have yet adopts it (`decide_basis`): the control takes the standard's key and library version; the standard's tested attributes are proposed for a person to decide, an attribute the control already states by wording is linked instead; its low-confidence attributes arrive with their question (`link_definitions`); the client's own attributes stay for a person to keep or retire; and the control is planned again with the rules, after which the plan goes through its approval as any other. A client's control keeps its own activity text (`refresh_statement` rewrites the description of a library copy only). A standard pending methodology review may be followed (decided by the product owner): the plan review raises a clarification that does not hold approval, linked to the standard on the Library. The decision is an audit event (`control.test_basis`).

On the control's Test plan tab, the **Test basis** card says what the plan is built from and from what, whether the client's RCM states a procedure of its own (most imported RCMs only restate that the control operated as described), the candidates with their status and rationale, and the decisions: find a standard or look again, follow a candidate as is, start from it and tailor, or use the client's procedures, each with the reason kept. The plan review's header names the basis; its holds link to the standard.

API: `GET …/controls/{control_id}/test-basis`, `POST …/test-basis/match`, `PUT …/test-basis` (`project.update` to match or decide; every project member reads). Web: `test-basis-model.ts`, `test-basis-view.tsx`, the route `/workspace/test-basis`.

## Depth: steps and evidence suites (milestone L3a, library version 4)

Requested by the product owner: the procedures read as one-liners, and the procedures and attributes are the foundation of the agents' tests, so they must be solid, with a standard suite of evidence per control. Decided by the product owner: numbered steps; a structured, keyed evidence catalogue; the IT general controls first; the Library page and the planner in this milestone, workpapers later.

**What a version 4 definition holds** (`testing_definitions.py`, built with `definitions_support.py`):

- **Procedures as steps.** Each procedure keeps its objective and a one-paragraph action (what a plan row shows) and adds numbered steps (`Step`): what the tester does, the evidence it uses (suite keys), what the workpaper records, and what to do when it does not hold. A sampled control runs: understand the design (read the procedure, record the client's values the test depends on, identify the information the performer relies on and how its reliability will be tested); walk one instance through, confirm the performers' authority and competence, assess the design against the risk; obtain and validate the population (AS 1105.10); select the sample at random with a recorded seed; test each item attribute by attribute; evaluate deviations for a person (AS 2201.48) and record the results; and at the roll-forward corroborate changes since interim, validate the remaining period's population, and test an update sample. A configured control inspects the setting against the policy, its scope, and its change history instead. The shared steps are worded once, in `definitions_support.py`, so every standard says them the same way; none decides anything a person must decide.
- **The evidence suite** (`EvidenceDef`). Per control, each item of evidence an engagement asks for: a key, its name, its form (system report, system log, system screen, configuration, ticket, document, policy, correspondence, observation, third-party report), who provides it, the phases it serves, its purpose (design, population, completeness, attribute evidence, context), what it must cover, what it must show field by field, how a population or its support is shown to be complete, what is sometimes offered instead and does not serve (a current user listing for a leaver's removal date; a list of tickets for a population of deployments), alternatives, and the attributes it supports. Steps and attributes refer to items by key; a key the suite does not define fails at import.
- **Attributes.** The IT general controls go from 51 to 76 attributes (65 tested). Each added attribute restates something the control's statement says (an approver who is not the user, every account of a leaver, a decision for every user on a listing, a conflict removed, a rerun that shows the data was processed once); where the statement states it but an RCM description might not, the attribute is MODERATE and marked as an inference. Values only the client knows stay LOW with their question, as before. Every version 2 attribute is still carried or retired with its reason.

**Checks** (`definition_registry.problems`, run by `test_testing_definitions.py`): a version 4 definition has a suite; every step names an action and what to record, no vague wording, only suite keys; a procedure that tests attributes does so in at least two steps with evidence; every attribute names its evidence keys; every suite item is used by a step or an attribute; a population or its support says how it is complete. The published document ([testing-definitions.md](testing-definitions.md)) now prints the steps under each procedure and the suite as a table, and a test keeps it equal to the code.

**Versions.** Each definition carries its version (`Definition.version`): the 19 IT general controls are 4, the other 34 stay 3 until their wave; `DEFINITIONS_VERSION` (4) is the highest and `LIBRARY_VERSION` is 4. An engagement control is linked to its definition and statement from version 3 (`DEFINED_SINCE`); a control below its definition's version is offered the update, which a person adopts as before (new attributes proposed, reworded ones mapped, retired ones retired with the note naming the version). Imports stamp the library version; adoption and matching stamp the definition's. A firm's approval of an entry is superseded when its approval is below the definition's version, not the library's: approving version 3 still stands for a business process control and reads as superseded for an IT general control.

**The planner.** A control that follows a version 4 standard (basis standard or customized, decided or with approved library attributes) gets its evidence requirements from the suite, phase by phase, instead of the generic rules (`evidence_planning._suite_requirements`): one requirement per suite item, worded for the control owner with what it must show, what makes it complete, and what is not acceptable; the population first, each item's attribute evidence depending on it with the sample selection stated, completeness support as report reliability, a change history as such, and context as optional. A configured control takes no sample. The engagement's own change requirements (a system or process change in the period) are kept. Every plan still passes `check_plan`; a test plans every version 4 standard. A control on the client's procedures is planned as before.

**The Library page.** Procedures show their numbered steps with the evidence each uses as keys that open the suite item, what to record, and what to do if it does not hold; the Evidence view opens with the standard evidence suite by phase, each item with its form and purpose, who provides it, what it covers and shows, when it is complete, what is not acceptable, alternatives, and the attributes it supports, then the items the control record names. The plan review's procedure rows link to the standard's steps ("Standard d-1: the steps") when the row is the standard's procedure.

Not in this milestone: steps and suite keys carried into plan rows and workpapers (the plan keeps its text and links out), the business process, entity-level, application, and key report controls (version 3 until L3b), and the new standard controls the library lacks.

## Breadth, wave 1: the IT general controls, application controls, and key reports the catalogue lacked (milestone L3c)

Requested by the product owner ("I see a lot missing on GITCs ITACs and BP. add all the missing controls with their standard attributes and procedures and evidence"). Decided by the product owner: the full lists proposed; the IT controls first, the business process, fixed asset, tax, and entity-level controls next; the 34 version 3 controls rewritten to version 4 after the new ones land.

Twenty-nine standard controls are added at version 4, each with a design statement, a library record, a definition as numbered steps, and an evidence suite, and each landing as pending methodology review:

| Area | Added |
| --- | --- |
| Logical access | ITGC-AC-07 access re-approved on transfer; AC-08 emergency (firefighter) access approved and its activity reviewed; AC-09 third-party accounts sponsored, time-limited, and reviewed; AC-10 segregation-of-duties conflicts detected and resolved; AC-11 direct database and operating-system access restricted and logged; AC-12 security events monitored |
| Change management | ITGC-CM-06 patches tested and approved; CM-07 projects follow the development life cycle; CM-08 data migrations reconciled and approved |
| IT operations | ITGC-OP-06 interfaces monitored; OP-07 service organization reports reviewed; OP-08 vulnerabilities remediated |
| Application controls | ITAC-03 duplicate invoices rejected; ITAC-04 purchase orders routed for approval; ITAC-05 invoices without a purchase order routed; ITAC-06 closed periods cannot be posted to; ITAC-07 journal entries above the threshold need approval; ITAC-08 prices come from the price master; ITAC-09 shipments billed once; ITAC-10 depreciation calculated by the system; ITAC-11 payroll calculated by the system; ITAC-12 postings validated; ITAC-13 interface totals checked |
| Key reports | IPE-03 inventory valuation report; IPE-04 fixed asset register; IPE-05 payroll register; IPE-06 billing report; IPE-07 accounts payable aging; IPE-08 key spreadsheets controlled |

**How they are written.** The IT general controls follow the shape of the version 4 rewrite: a design procedure that reads the procedure and records the client's values, a walkthrough that confirms authority and assesses the design, population validation and random selection, attribute-by-attribute testing, deviation evaluation for a person, and the roll-forward. An application control is a test of one (`definitions_itac._automated`): the configuration against its approved design or the client's criterion (a delegation of authority, an approval matrix, a threshold, a discount limit, which stay LOW with their question until the client provides them), one instance showing it operates, and the configuration's change history, relying on the access and change-management controls between the dates inspected (AS 2201.B28-.B33). A key report is validated before use (`definitions_ipe._report`): parameters against the definition and the period, the total re-agreed to the ledger or source, the preparer's item check re-performed, and the sign-off before use; the extent of the item check is the client's. The spreadsheet control (IPE-08) tests access and versions, inputs against source, formulas against documented logic, and the owner's sign-off on the version used.

**Service organizations.** ITGC-OP-07 is the review of a service organization's SOC 1 report that the data-center control (ITGC-OP-05) deferred; a hosted system scopes OP-05 out and OP-07 in. The planner's category mapping now reads a report's logic document as report-reliability evidence, so a key report's design is planned from its suite.

**Matching.** Each new standard has a signal in `library_matching.SIGNALS`, and the specific standards displace the general ones they overlap (firefighter over privileged, transfer and third-party over provisioning, patching, SDLC, and migration over change approval, interfaces over job monitoring, security monitoring over incidents). The scenario set grows to thirty-one RCM-worded controls, one per new standard, each found as a strong candidate; the pricing configuration that was a negative is now the price-master standard, and a hedge designation review stands in as a control the library still lacks.

**What an engagement sees.** The library index lists 82 standard controls; system scoping's recommended set per layer is unchanged (the new controls are available to add, not recommended by default); nothing in an existing engagement changes until a person adds a control or follows a standard.

Not in this wave: the business process, fixed asset, tax, and entity-level additions (wave 2), and version 4 depth for the 34 version 3 controls (L3b).
